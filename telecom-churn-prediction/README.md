# Отток клиентов телеком-оператора «ТелеДом»

## Задача

Оператор связи хочет заранее находить абонентов, готовых расторгнуть договор,
чтобы предлагать им промокоды и спецусловия адресно, а не всей базе подряд.
Нужна модель, предсказывающая вероятность оттока по персональным данным,
тарифу и набору подключённых услуг.

**Целевая метрика:** ROC-AUC.

## Данные

Четыре таблицы в SQLite (`contract`, `personal`, `internet`, `phone`), объединённые
одним SQL-запросом с `LEFT JOIN` по `customerID` — 7043 абонента, 20 признаков после
объединения. Данные предоставлены курсом и не публикуются.

Ключевые поля: тип и способ оплаты, ежемесячные и накопленные платежи, дата начала
и окончания обслуживания (используется только для целевого признака), набор
подключённых интернет- и телефонных услуг.

## Что было сделано

- Выгрузка и объединение четырёх таблиц одним SQL-запросом
- Целевой признак (`churn`) сконструирован из даты окончания договора
- Признак длительности обслуживания взят из накопленных платежей (`TotalCharges / MonthlyCharges`), а не из дат напрямую — исходный вариант через даты давал утечку (см. «Что бы сделал иначе»)
- Отбор признаков и корреляционный анализ только по train, чтобы не заглядывать в test
- Сравнение шести моделей: Dummy, логистическая регрессия, случайный лес, LightGBM, CatBoost, XGBoost — с кросс-валидацией и подбором гиперпараметров
- Подбор порога классификации под бизнес-задачу (отбор группы риска, а не порог 0.5 по умолчанию)
- Permutation importance для важности признаков (устойчива к one-hot-кодированию, в отличие от встроенной важности бустинга)

## Результат

| Модель | CV ROC-AUC |
|---|---|
| Dummy (baseline) | 0.50 |
| Logistic Regression | 0.77 |
| Random Forest | 0.82 |
| LightGBM | 0.82 |
| CatBoost | 0.83 |
| **XGBoost** | **0.83** |

XGBoost и CatBoost статистически неразличимы (расходятся меньше чем на одно
стандартное отклонение CV), но XGBoost чуть впереди по чистому значению.
**ROC-AUC на тесте: 0.82.**

Наибольший вклад в предсказание вносят: длительность обслуживания, тип договора,
накопленные платежи.

**Вывод:** при пороге 0.35 модель относит в группу риска 37% базы и ловит в ней
около 78% реально уходящих клиентов — более чем двукратный выигрыш по сравнению
со случайным отбором того же объёма.

## Что бы сделал иначе

Первая версия признака длительности обслуживания считалась от дат `BeginDate`/`EndDate`
и давала ROC-AUC 0.92 на тесте против 0.90 на кросс-валидации — подозрительно, тест не
должен быть выше CV. Контролируемый эксперимент показал: дело не в том, что признак
посчитан от дат, а в том, что он был посчитан **в днях**, а не в месяцах — при округлении
до месяцев метрика честно падает до 0.83 и на CV, и на тесте одновременно. Похоже, точный
день начала/окончания договора в этом синтетическом датасете статистически связан с
оттоком через артефакт генерации дат, а не через содержательный сигнал. Предпочёл более
скромную, но объяснимую метрику вместо эффектной, но необоснованной.
