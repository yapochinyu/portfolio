# Heart Disease Prediction — демонстрационный модуль для МИАЦ РСО-Алания

Демонстрационный модуль, разработанный в рамках производственной практики
для Медицинского информационно-аналитического центра Республики Северная
Осетия — Алания (МИАЦ РСО-Алания). Задача — показать на практике, как может
выглядеть сервис предварительной оценки риска сердечно-сосудистого
заболевания по клиническим показателям пациента: от модели до рабочего API,
который можно вызвать из внешней системы.

Поскольку это учебно-демонстрационный проект, а не внедрение в реальную
медицинскую информационную систему, модель обучена на открытом наборе данных
(см. «Данные» ниже), а не на данных пациентов центра — цель показать
работоспособность подхода и архитектуру решения, а не заменить собой
диагностику.

---

## Постановка задачи

Сердечно-сосудистые заболевания — одна из главных причин смертности, и
раннее выявление пациентов группы риска напрямую влияет на то, кого в первую
очередь направят на углублённое обследование. Модуль показывает, как по
базовым клиническим показателям (доступным уже на этапе амбулаторного приёма,
без сложных инструментальных исследований) можно получить оценку вероятности
заболевания — и как эту оценку отдать наружу простым HTTP-запросом, чтобы её
можно было встроить в информационную систему медицинского учреждения.

---

## Данные

Использован открытый датасет [Heart Failure Prediction](https://www.kaggle.com/datasets/fedesoriano/heart-failure-prediction/data)
(Kaggle) — 918 наблюдений, 11 клинических признаков:

- `Age` — возраст
- `Sex` — пол
- `ChestPainType` — тип боли в груди
- `RestingBP` — артериальное давление в покое
- `Cholesterol` — уровень холестерина
- `FastingBS` — повышенный сахар натощак (>120 mg/dl)
- `RestingECG` — результаты ЭКГ
- `MaxHR` — максимальный пульс
- `ExerciseAngina` — стенокардия при нагрузке
- `Oldpeak` — депрессия сегмента ST
- `ST_Slope` — наклон сегмента ST

Целевая переменная — `HeartDisease` (1 — заболевание есть, 0 — нет).

---

## Что было сделано

1. Первичное ознакомление с данными, проверка пропусков и дубликатов, поиск аномалий
2. EDA: распределения признаков, доли категорий, связь с целевой переменной
3. Подготовка признаков: заполнение пропусков, кодирование категориальных, масштабирование числовых — всё внутри `Pipeline`
4. Сравнение четырёх моделей (Logistic Regression, Random Forest, XGBoost, LightGBM) кросс-валидацией
5. Выбор лучшей модели, сохранение обученного пайплайна (`preprocessing + модель`)
6. Обёртка модели в API на FastAPI — то, что превращает ноутбук в демонстрируемый сервис, а не просто отчёт

---

## Результат

Train/test разбиение 80/20, стратифицированное. Модели сравнивались
5-фолдовой кросс-валидацией на train:

| Модель | ROC-AUC (CV) | Recall (CV) | F1 (CV) |
|---|---|---|---|
| **Random Forest** | **0.93** | **0.92** | **0.89** |
| XGBoost | 0.92 | 0.90 | 0.89 |
| LightGBM | 0.92 | 0.88 | 0.87 |
| Logistic Regression | 0.92 | 0.89 | 0.88 |

Лучшая модель — **Random Forest**, с небольшим отрывом от остальных.

**Проверка на отложенном тесте** (184 наблюдения, модель их не видела ни на
обучении, ни при выборе модели):

| Метрика | CV (train) | Тест |
|---|---|---|
| ROC-AUC | 0.93 | **0.92** |
| Recall | 0.92 | **0.91** |
| F1 | 0.89 | **0.88** |

Тестовые метрики почти не отличаются от кросс-валидационных — переобучения
под train нет. Из 102 пациентов с заболеванием в тесте модель находит 93
(recall 0.91), из 82 здоровых — верно распознаёт 65 (specificity ≈0.79):
модель заметно консервативнее в сторону «лучше перепроверить», чем «лучше
пропустить», что и требуется для скрининга.

Recall выбран одним из ключевых критериев осознанно: для скрининга риска
дороже пропустить действительно больного пациента (ложноотрицательный),
чем направить здорового на дополнительную проверку (ложноположительный).

```

│   heart.csv                        — обучающие данные
```

## Установка и запуск

### 1. Клонирование репозитория

```bash
git clone https://github.com/yapochinyu/heart-disease-prediction.git
cd heart-disease-prediction
```

### 2. Создание окружения

Окружений два — под разные задачи: `heart-research` для запуска ноутбука,
`heart-api` для запуска сервиса.

Чтобы воспроизвести ноутбук:
```powershell
conda env create -f envs/heart-research.yml
conda activate heart-disease-research-env
```

Чтобы запустить API:
```powershell
conda env create -f envs/heart-api.yml
conda activate heart-api
```

### 3. Запуск API
```powershell
uvicorn api.app:app --reload
```

### 4. Открыть документацию
```
http://127.0.0.1:8000/docs
```

### Пример запроса

```JSON
{
  "Age": 54,
  "Sex": "M",
  "ChestPainType": "ATA",
  "RestingBP": 130,
  "Cholesterol": 250,
  "FastingBS": 0,
  "RestingECG": "Normal",
  "MaxHR": 150,
  "ExerciseAngina": "N",
  "Oldpeak": 1.0,
  "ST_Slope": "Up"
}
```

Ответ API на этот запрос:
```JSON
{
  "prediction": 0,
  "probability": 0.07
}
```

(`probability` — вероятность наличия заболевания; в этом примере показатели
пациента модель относит к низкому риску.)

**Важно:** модель ожидает данные в том же формате, что и при обучении, все
категориальные значения должны совпадать с обучающими — обработка данных
встроена в pipeline, но не подменяет собой валидацию входа на стороне API.
